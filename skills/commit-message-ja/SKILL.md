# コミットメッセージ作成（Conventional Commits / 日本語）

ステージ済みの差分から、Conventional Commits 形式で日本語のコミットメッセージを作成する。
**型(type)だけは英小文字**、**件名と本文の説明はすべて日本語**で書くのがこの規約の要点。

## フォーマット

```
<type>: <日本語の件名>

<日本語の本文（任意・複数論点があれば箇条書き）>

<フッター（任意）>
```

- 1 行目（件名）= `type: ` + 日本語の要約。`type` と `:` の後に半角スペース 1 つ。
- 件名は簡潔に（目安 50 文字前後まで）。末尾に句点「。」は付けない。
- 本文が必要なときは件名の後に空行を 1 行入れてから書く。
- 関連チケットがあればフッターに `Refs: <KEY-NNN>` を付ける。

## 手順

1. **ステージ内容を確認する**
   - `git diff --cached --stat` で対象ファイルを把握。必要なら `git diff --cached` で中身を読む。
   - 何もステージされていなければ `git status` を見せ、何をコミットしたいか／ステージするかをユーザーに確認する（勝手に `git add -A` しない）。
2. **type を決める**（下表。複数該当する場合は「変更の主目的」で 1 つ選ぶ）。
3. **件名を日本語で書く**：`type: ` に続けて、何をしたかを簡潔に。
4. **本文を付ける**（任意）：論点が複数あるときは日本語の箇条書き（`- `）で要点を列挙。なぜ・何を変えたかを書く。
5. **フッターを付ける**（任意）：チケット番号があれば `Refs: <KEY-NNN>`。破壊的変更があれば `BREAKING CHANGE: <説明>`。
6. **まず案を提示して確認を取る**。ユーザーが承認するまで `git commit` は実行しない。

## type の選び方

| type | 使う場面 |
| --- | --- |
| `feat` | 新機能・新しい振る舞い・新しい手段の追加 |
| `fix` | バグ修正 |
| `refactor` | 振る舞いを変えないコード/構成の整理・リネーム・移動 |
| `docs` | ドキュメントのみの変更（README・コメント等） |
| `style` | 整形・空白・セミコロンなど、ロジックに影響しない変更 |
| `test` | テストの追加・修正 |
| `chore` | ビルド以外の雑務（依存更新・設定・補助スクリプト等） |
| `perf` | パフォーマンス改善 |
| `ci` | CI 設定・スクリプトの変更 |
| `build` | ビルドシステム・外部依存に関する変更 |
| `revert` | 変更の取り消し |

迷ったら「この差分の主目的は何か」で判断する。例：リネームとドキュメント更新が混在していても、
狙いが新しい仕組みの導入なら `feat`、見た目上の整理が主なら `refactor`。

## 例

単一の変更：

```
fix: ログイン時のトークン期限切れで無限ループする不具合を修正
```

複数論点をまとめる：

```
feat: skills.sh対応とスキル単位＋lock管理への移行

- 同名衝突を避けるため重複スキルをフレームワーク接尾辞付きにリネーム
- README を skills.sh 中心に再構成し、運用ルールと注意点を追記
- install.sh に skills.sh 推奨の告知を追加

Refs: {ticket_id}
```

## コミットを実行するとき

- ユーザーが承認・依頼したときのみ `git commit` する。
- デフォルトブランチ上なら、コミット前にブランチを切る（環境のルールに従う）。
- AI アシスタントがコミットする環境ルールで Co-Authored-By トレーラーの付与が求められている場合は、
  本文の末尾（フッター）にそのトレーラーを追加する。
- 件名・本文に API キー / トークン / パスワード等の機密情報を含めない。
